# 山海行笺综合优化方案

日期：2026-09-17。范围：当前本地项目的体验、AI 效果、性能与稳定性。

> 本文保留实施前的评估与当时验证结果。后续四套方案的实现范围、限制和本轮验证另见 [OPTIMIZATION_IMPLEMENTATION.md](OPTIMIZATION_IMPLEMENTATION.md)，下文源码行号及问题描述属于评估时快照。

建议先完成「编辑内容不丢、生成流程不中断、版本行为一致」，再推进 AI 上下文优化、历史分页和运营能力。以下四套方案可分别实施，也可按文末顺序组合。

## 评估依据与当前基础

已阅读 AGENTS.md、PRD、开发与验收文档，并核查前端工作区状态、编辑组件、聊天入口、AI 工具、版本服务、缓存、数据库结构及测试。

项目已有结构化 AI 编辑、严格 Schema、事务与版本校验、用户权限、正常取消和超时处理、地图双层缓存、同参数请求合并、CI 和隔离验收脚本。优化应在这些能力上继续完善。

本次执行 `bun run check`：lint、typecheck 通过，16 个测试文件、125 项测试全部通过。使用临时进程内的 dummy 配置和现有隔离测试；Windows 启动器按既有验收文档统一 PATH，项目命令仍由 Bun 执行。本次没有运行浏览器验收、性能压测、生产构建或真实 AI／百度联调。

下述现状来自源码；交互问题尚未进行浏览器复现，性能收益尚未测量。工期按一位熟悉项目的全栈开发者估算，包含相关测试，不是交付承诺；各方案存在共用工作，组合时应重新估算。

## 方案 A：体验改进

### 当前问题

- 地点与食记编辑器在当前工作区 ID 变化时清空编辑状态；即使使用 KeepAlive，也无法恢复该编辑会话。见 [MapView.vue](../app/components/MapView.vue#L191)、[FoodJournalView.vue](../app/components/FoodJournalView.vue#L118)。
- 打开同一规划的预览或设置，也会执行 `beginNavigation()` 中的 `stop()`，因此查看行程会中止正在生成的回复。见 [useWorkspace.ts](../app/composables/useWorkspace.ts#L159)，同文件第 287、303 行为对应入口。
- 保存冲突后，目前主要提示用户自行保留内容、取消编辑并重新打开。首次创建已有三个推荐提示词，可继续补充结构化需求引导。移动端抽屉还可补齐焦点和键盘行为。

### 实施内容

1. **统一草稿管理。** 按用户、规划、编辑对象保存草稿，记录它基于的修订信息；支持切换后恢复、刷新后恢复、明确显示未保存状态。收到 409 时保留草稿并展示最新内容，让用户选择如何应用；首期不自动合并有冲突的字段。
2. **查看预览时继续生成。** 分离视图切换和 AI 任务生命周期；同一规划中打开总览、食记或设置时保留生成，提供持续可见的状态与停止按钮。首期跨规划切换可沿用明确停止策略，把跨规划后台生成留作后续扩展。
3. **增加轻量创建引导。** 在现有欢迎页中提供目的地、天数、预算、出行人数和节奏选项，生成可编辑的首条消息；保留直接输入入口。初期将这些作为对话需求，不为尚未决定的业务字段扩张行程 JSON。
4. **移动端与键盘打磨。** 抽屉关闭时移出焦点顺序，支持 Escape 和焦点归还；页签支持方向键；验证手机软键盘打开时输入框与发送按钮可达。沿用现有国风设计令牌和两栏布局。

### 收益与验收

- 填写地点或食记后 A→B→A、刷新或保存冲突，草稿仍可恢复；退出换号不显示上个账号的草稿。
- 模拟慢速 AI 回复时，在同规划对话与总览间切换，回复完整且只完成一次落库；明确停止仍立即生效。
- 用户从创建引导发出第一条需求，无需理解规划 JSON、工具参数或版本机制。
- 手机横竖屏、软键盘和纯键盘操作均完成创建、编辑、保存流程。

主要成本在草稿生命周期和生成任务归属；必须保留现有的过期响应拦截与用户隔离。

## 方案 B：AI 质量与编辑可靠性

### 当前问题

- `apply_plan_edits` 已支持同一轮原地更新一个版本；但 AI 的 `patch_plan_json` 经 `patchPlan()` 直接进入 `commitVersion()`，没有复用同轮合并和无变化跳过逻辑。混用工具会产生额外版本。见 [tools.ts](../server/agents/tools.ts#L74)、[plan.ts](../server/services/plan.ts#L288)。
- 当前乐观锁比较展示版本号，而同轮 AI 可以修改内容却保持版本号。例如另一设备读到 v2 后，AI 继续更新同一个 v2，旧设备仍携带 `expectedVersion: 2` 保存时无法识别这一段变化。这是已有锁的特定边界，不表示所有并发检查都失效。见 [版本比较](../server/services/plan.ts#L61)与[同轮更新](../server/services/plan.ts#L155)。
- 每轮注入完整规划 JSON，并保留最多 60 条历史文字、每条最多 20,000 字符，没有总输入预算。长行程叠加长会话可能触及模型上下文限制。见 [travel-agent.ts](../server/agents/travel-agent.ts#L37)、[chat.ts](../shared/schemas/chat.ts#L26)。
- 现有 Schema 能验证结构和字段范围；日期顺序、每日安排密度、预算明细等业务质量，还可增加明确的检查结果。

### 实施内容

1. **统一两种 AI 工具的提交规则。** 共用事务提交入口、无变化判断和同轮版本复用；发生版本切换或进入下一轮时按既有规则追加分支。
2. **分离展示版本与数据修订号。** 在规划记录增加单调递增的 `revision`；每次实际内容修改或版本指针切换都递增，以它检测陈旧保存。AI 执行侧维护已读取的 revision，冲突后重读；模型不负责猜测修订号。新增 DB 字段通过 Drizzle migration，同步接口契约与客户端。
3. **建立上下文预算。** 优先保留当前请求、必要约束、相关规划事实和最近对话；旧历史压缩为带来源范围的摘要。长规划按日或模块读取，保留取得完整相关内容的工具入口；最终写入仍由服务端对完整 PlanSchema 校验。先做确定性的体积限制，再用实际模型 usage 校准 token 预算。
4. **增加行程检查与针对性修正。** 显示日期格式或顺序异常、重复地点、停留时间过密、预算明细不一致等提示。费用统计先定义口径，区分食记与行程费用，避免重复计算。未知开放时间、票价、交通耗时保持待核实，不把规则检查当作实时事实验证。
5. **建立小规模固定评测集。** 约 30 个样例覆盖新增行程、移动景点、预算变更、跨天调整、字段纠错、取消、版本冲突与回滚后再编辑。离线模型覆盖协议和存储行为；真实模型另以受控预算评估完成率、工具纠错次数、耗时和输入量。

### 收益与验收

- 同轮 `apply → patch → apply` 在当前版本未被移走时只保留一个版本；无变化编辑不增加版本；分叉规则保持正确。
- 模拟 AI 同版本继续更新后，另一设备的旧 revision 保存返回 409，已保存内容保留。
- 长行程与长对话样例不超过配置的输入预算，关键约束可追溯；摘要不覆盖当前规划事实。
- 对缺坐标、日期异常、重复地点和预算差异给出可理解的检查结果；修正始终经过结构化编辑与版本记录。
- 记录评测基线后再设通过率目标，不预先承诺模型效果或费用下降比例。

独立 revision 也是后续规划缓存新鲜度判断的基础，应先于强缓存实施。

## 方案 C：性能提效

### 当前问题

- 保存或回复结束后会重取规划详情、版本列表、账号下规划列表、会话列表，再重取当前会话消息；会话空闲且归属匹配时为 5 次 GET。见 [useWorkspace.ts](../app/composables/useWorkspace.ts#L403)。
- 消息接口只返回最近 200 条；版本接口只返回最近 200 个，没有继续翻页入口。更早数据仍在数据库，但 UI 无法完整浏览。见 [conversation.ts](../server/services/conversation.ts#L57)、[versions.get.ts](../server/api/plans/[id]/versions.get.ts#L8)。
- 街景 URL 直接绑定角度和视野滑块，变化后立即触发取图。已有取消和缓存不能避免所有不同参数的请求。见 [PanoramaView.vue](../app/components/PanoramaView.vue#L14)、[CachedImage.vue](../app/components/CachedImage.vue#L9)。
- IndexedDB 每次写入后读取全部条目并排序清理，包括图片 Blob；限制条数但没有字节预算。后端会判断过期，但没有自动分批回收过期记录。见 [idb.ts](../app/utils/idb.ts#L124)、[cache.ts](../server/services/cache.ts#L45)。
- 聊天区深度监听整个消息数组，流式文本交给 MDC 更新；重型视图和长记录可进一步按需加载。是否构成实际卡顿，需要先测量。

### 实施内容

1. **用局部更新替代无差别刷新。** 保存接口返回足够的新状态与 revision，前端更新当前规划和受影响列表项；版本详情、旧消息、其他工作区会话按需请求。保留完成后的必要对账请求和过期响应保护。
2. **补齐游标分页。** 消息使用 `(createdAt, id)`，版本使用版本号分页，规划与会话列表也限制首批大小；版本树补齐祖先或明确表示尚未加载的历史，不把缺失父节点画成真实根节点。界面完整历史与 AI 上下文窗口分开管理。
3. **接通规划缓存。** 现有 `fetchJsonCached()` 尚未接入规划详情；应增加身份隔离、revision/ETag 校验和保存后失效策略。缓存快照先展示、后台检查新鲜度，离线时标明只读状态；不直接以一小时 TTL 代替版本校验。
4. **按需取图。** 街景滑块停止拖动或防抖后才请求；图片接近视口时加载；暂停失活面板的监听请求，避免保留的旧面板跟随全局规划变化取图；前端同 URL 合并请求，取消由订阅计数管理，避免一个图片组件取消其他组件共享的请求。
5. **限制缓存体积。** 前端记录字节数和访问索引，分批淘汰；后端增加过期索引、分批清理和容量策略；后台列表使用 SQL `length(value)` 统计大小，避免读取图片正文。缓存清理只处理缓存数据。
6. **优化加载与流式渲染。** 根据构建分析对 Markdown 编辑器、非当前面板做条件式异步加载；滚动更新按动画帧合并，只观察必要的末条消息变化；历史预览默认摘要。先分页，若实测 DOM 或脚本耗时仍高，再增加长列表虚拟渲染。按需加载及长列表优化可参考 [Vue 官方性能指南](https://vuejs.org/guide/best-practices/performance)；Nuxt 的 Lazy 组件应与条件渲染配合，见 [Nuxt 组件文档](https://nuxt.com/docs/4.x/directory-structure/app/components)。

### 收益与验收

- 在固定设备与网络条件下，先记录工作区切换耗时、单次保存 GET 数、响应体积、流式更新脚本耗时和图片请求数，再对比优化结果。
- 普通局部保存不重新读取全账号规划和会话列表，额外 GET 以不超过 2 次为初始设计目标。
- 用 100 个规划、单会话 1,000 条消息、单规划 500 个版本的合成数据验证：首批有界，旧记录可完整翻阅，无重复或漏项，当前旧版本仍可定位。
- 持续拖动街景滑块时只提交最终参数或少量受控请求；屏外和失活面板不会发起不必要请求。
- 缓存超过配置容量后分批回落，换号隔离、过期判断和已有后端请求合并测试继续通过。

性能指标是待测目标。首屏总 JS、加载耗时与并发容量不能从现有文件大小或测试通过情况推导。

## 方案 D：上线稳定性

### 当前问题

- AI 工具会先提交规划版本，而助手文本、工具结果和预览主要在流结束时统一回写。正常取消和超时已有处理；进程异常退出时仍可能出现规划已改、回复为空的情况。见 [chat.post.ts](../server/api/chat.post.ts#L45)。
- 当前 AI 活动锁按规划、按进程生效，没有应用层的用户级和全局生成额度。多规划同时生成需要独立的用量管理。
- 后台 `staticMaps` 使用所有 image 缓存条目数，`panoramaImages` 读取当前图片链路未写入的 `panoramas` 表，不能代表真实外部调用次数。见 [stats.get.ts](../server/api/admin/stats.get.ts#L24)。
- 已有 CI 执行 check 和 build，也已有自包含 HTTP 隔离验收脚本；可把浏览器关键流程及恢复验证纳入发布检查。

### 实施内容

1. **记录生成任务状态与检查点。** 增加运行 ID、开始时间、状态、最后完成步骤和关联版本；在工具完成及有界时间间隔保存检查点。重启后把未完成运行标记为中断，恢复已提交变更的预览。首期恢复结果和状态，不承诺无缝续传尚未落库的 token。
2. **对重试提供幂等性。** 请求携带唯一 ID，服务端识别重复提交；变更事件与规划更新同事务保存，再用于恢复聊天展示。重复请求返回已有状态，避免重新执行已提交的非幂等编辑。沿用唯一 Drizzle 写入路径。
3. **真实指标与用量保护。** 在 AI 和地图外部请求边界记录耗时、成功/失败、缓存命中、步骤数及供应商实际提供的 usage。分别配置用户与全局并发和周期额度，界面显示等待或限额原因；不可用的 token 指标明确标记未知。日志保留请求 ID 和脱敏诊断信息。
4. **完善发布验收。** 将现有 `scripts/verify-isolated.ts` 作为构建后的隔离验收入口；加入模拟 AI 的浏览器流程，覆盖登录、创建、生成、修改、版本切换、刷新恢复、移动端与退出换号。
5. **建立恢复演练。** 为 SQLite 设计一致性备份及恢复验证，用独立副本验证用户、规划、版本和会话恢复。先按当前单实例架构运行；若以后需要多实例，再单独设计共享任务协调，不能将进程内 Set 视为跨实例锁。

### 收益与验收

- 在工具成功但流未结束时模拟进程退出：重启后规划与关联变更可见，任务明确显示中断状态。
- 重复发送同一请求 ID，不重复创建用户消息或执行已提交编辑；取消和失败后正确释放并发名额。
- 模拟一次未命中、两次命中和一次外部失败，后台统计可逐项对账；缓存条目数和外部调用次数分开展示。
- 发布检查使用临时数据库、dummy 配置和模拟外部服务，失败能定位到请求或步骤；恢复演练通过后再宣称具备相应恢复能力。

## 建议实施顺序

| 阶段 | 优先任务 | 完成后的直接效果 |
| --- | --- | --- |
| 第一批 | B：统一 AI 提交与 revision；A：地点/食记草稿恢复 | 减少版本噪声，旧快照不会悄悄覆盖新内容，切换后无需重填 |
| 第二批 | A：同规划查看预览不中断生成；B：上下文预算与固定评测；C：局部刷新和历史分页 | 对话更连续，长记录可找回，减少不必要等待 |
| 第三批 | C：取图、缓存体积、渲染优化；D：恢复、指标、额度和发布检查 | 长期使用更可控，为多用户和上线提供可验证基础 |

如果近期准备对外开放，把 D 的恢复、额度和发布检查提前到第二批。创建引导、行程检查和视觉细节可穿插实施，但不应挤占内容保存与恢复的工作。

四套方案沿用 Nuxt、Bun、SQLite、Drizzle、Mastra 与现有 AI SDK 协议；地图继续使用服务端静态图和全景。在线地点搜索、实时票价和道路导航属于现有 PRD 之外的产品扩展，需要另行确定数据来源、服务成本与契约。

本次交付为优化方案文档，业务代码未改动；实际实施时按每批改动执行相关回归、项目质量检查及明确列出的验收。
