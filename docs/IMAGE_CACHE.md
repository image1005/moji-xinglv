# 图片缓存：前端与服务器

2026-09-22，用户确认图片7天、搜索命中1天。继续使用现有Nuxt/Bun、IndexedDB、Nitro storage和Drizzle/SQLite，不新增依赖、数据库迁移或存储服务。真实业务数据与.env保持原样。

## 请求路径与失效规则

| 层 | 保存内容 | 有效期与限制 |
| --- | --- | --- |
| 浏览器IndexedDB | 当前账号的图片Blob及容量/访问元数据 | 7天；图片与规划缓存共用48 MiB/300条上限，先清过期、再按最近访问淘汰 |
| 服务端Nitro L1 / SQLite L2 | 实际下载、解码并转WebP的公开推荐图字节 | 7天；复用既有512 MiB默认总缓存预算，定时分批维护；冷L1从SQLite回填 |
| 服务端最终选图 | 已确认图片、来源、署名、匹配名称 | 1天；按规范化名称候选、城市、地址、实体类型和腾讯启用状态复用，不使用规划ID或数组下标 |
| 腾讯搜索 | 官方接口返回并经校验的候选列表 | 有候选1天；空列表10分钟；请求失败不缓存 |
| Wikimedia匹配 | 精确匹配与Commons元数据 | 命中1天；无匹配1小时；显式缺图重查可绕过负缓存 |

刷新页面后，先取得当前规划与资源身份，再从IndexedDB取图；图片缓存命中时不向服务器下载该图。IndexedDB不可用时降级为正常网络请求，仍可使用服务器缓存。

服务器收到资源图片请求后先验证用户、规划、实体、指纹和图片键，再读L1→SQLite→供应商。L1清空后仍可从SQLite恢复字节。跨工作区仅复用公开推荐图选图/字节；附件继续使用私有附件表与权限接口，不参加公开推荐图缓存。

实体名称/城市/地址变化会改变指纹；同一实体改用另一图片时改变图片键。服务端生成 `.../resource-image?entityId=...&v=...&image=...`，浏览器按完整URL缓存。旧图片键不能读取替换后的图片，返回404；未带新参数的历史请求继续兼容。资源更新不增加行程revision/版本。

## 重试与并发

- 普通加载复用有效缓存。图片框中的“重试”删除该URL的本地Blob和元数据，以HTTP reload重新请求；不清空其它照片、规划或草稿。图鉴的“重新查找图片与定位”仍是独立的供应商资源检索操作，不无条件绕过所有正缓存。
- 新下载仅接受非空、不超过8 MiB的JPEG/PNG/WebP。支持createImageBitmap的浏览器先解码再缓存；旧坏缓存由图片加载错误提示引导重试。推荐图片在服务器端始终由sharp实际解码，限制5 MiB输入与2400万像素。
- 前端同一账号/URL/加载方式共享请求，取消单个订阅不影响其他订阅；退出/切换账号终止旧请求并隔离缓存。最后一个订阅取消才终止前端网络请求。
- 服务端同一来源图共享缓存读取、下载及解码；最多12个独立任务，每次网络下载12秒超时。某个消费者取消只停止其等待，不中断别人的共享任务；已经开始的有界下载可继续完成并进入缓存。
- 公开地点的最终选图也合并并发，第二个工作区复用同一结果，不再次支付腾讯查询。网络失败、解析失败和解码失败不会写成成功或无匹配缓存。

资源代理保持 `Cache-Control: private, no-store`，避免Cookie用户切换后浏览器HTTP缓存绕过服务端身份；应用持久缓存由有账号隔离的IndexedDB管理。百度代理沿用既有专用缓存头和并发逻辑。

## 验证方式

`bun run check` 包括缓存未命中并发合并、取消互不影响、失败重试、7天TTL、腾讯命中1天/空结果10分钟、跨工作区选图复用以及前端坏内容拒绝。`bun run verify:media` 在临时SQLite验证冷L1命中持久层且不访问外网、缓存命中仍拒绝越权、更换图片改变URL和旧键拒绝。`bun run test:product` 使用真实浏览器IndexedDB检查刷新不增加图片HTTP请求，以及损坏本地缓存后一次重试恢复。完整本轮结果见 [VERIFICATION.md](VERIFICATION.md)。

隔离测试中的照片和供应商均为明确测试夹具；此次缓存改动不改变腾讯云/百度等真实服务凭据的联调边界。没有通过重复调用付费服务验证本地缓存。
