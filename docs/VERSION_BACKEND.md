# 版本后端与共享契约

本次修改将 AI 运行中成果和正式历史版本分开持久化，保留已有历史、分支、展示版本号及独立的规划修订号。前端保存入口、版本树和改名界面由并行任务接入；本文区分后端已提供的行为与仍需前端联调的部分。

## 原有问题与保存入口

修改前的 `server/services/plan.ts` 已有两项去重，不能当成缺失功能重新实现：`commitMutation` 比较规范化后的 JSON，相同内容返回 `skipped`；`commitAiTurn` 用 `assistantMessageId` 找到该轮当前版本并原地合并。

实际问题在于保存消息与版本终态：

| 入口 | 原有行为与问题 | 本次行为 |
| --- | --- | --- |
| 聊天预览卡片的保存 | AI 已自动提交版本，按钮调用不带新 JSON 的 `/save`；版本去重生效，但 `savePlanVersion` 仍无条件插入“无变化”系统消息 | 无变化先校验 revision，再返回 `skipped`；不新增版本或保存消息 |
| 手工表单保存、规划资料编辑 | 内容变化时新增版本，使用独立 revision 校验；Markdown 正文有自己的修订处理 | 保留独立有效保存，不按时间窗口合并不同操作 |
| `apply_plan_edits` / `patch_plan_json` | 每次有效工具调用立即写正式快照；同轮通常合并，但中途切换后会再次追加，完整完成与部分失败结果难以区分 | 同轮编辑只更新持久化草稿和预览，完成收尾时正式提交一次 |
| `finishRun` / `recoverInterruptedRuns` | 仅更新任务状态，部分工具结果已作为正式版本写入，上一成功结果可能已被替换 | 正常终态事务提交最终有效结果；异常终态保留上一成功结果及可恢复草稿 |
| 请求重试 | `chat_runs` 已通过用户与 requestId 拒绝重复执行 | 保留既有请求幂等机制，结束后的迟到工具不能继续写入 |

“好版本”仅指通过结构校验并成功提交的有效结果；AI 不评价、清理或删除历史。新行为不会批量改写或清除旧版本。

## 正式版本、草稿与并发

`plans.plan_json` 与 `current_version_id` 始终表示上一成功正式结果。运行中的有效编辑保存到 `plan_run_drafts`，每轮一条；助手预览在同一事务中更新，草稿不进入正式版本列表。每次有效草稿变化推进规划 `revision`，同轮下一步工具继续读取该草稿；普通规划查询和手工保存读取正式快照。

草稿记录原父版本、基线修订号和最新修订号。运行期间的手工保存或历史切换会使草稿基线过期；AI 不能通过重读绕过冲突，完成时也不能覆盖新结果。失败、取消、超时和服务重启保留可恢复部分成果。用户查看草稿后，可以带当前修订号显式恢复；恢复不自动合并当前规划与旧草稿。

正常完成只追加最终内容变化的一个正式版本，父节点为开始编辑时的当前版本；同轮编辑后又完全还原基线时不新增版本。历史切换继续只移动指针，随后新增正式版本使用 `max(version) + 1`，父节点指向切换后的版本，保留分支。已完成版本的行程快照不再原地被后续 AI 工具改写。

恢复闭环使用 `GET /api/plans/:id/drafts` 列表、`GET /api/plans/:id/drafts/:draftId` 查看完整成果，以及 `POST /api/plans/:id/drafts/:draftId/restore` 确认恢复。恢复请求必须带当前 `expectedRevision`，可同时携带 `expectedVersion` 和授权会话 `conversationId`；结果兼容保存接口。恢复成功后，原助手预览标为 `recovered` 并关联用户确认的正式版本，原运行仍保留异常终态。重复恢复只返回之前处理过的版本，不再次改变当前指针；调用方随后刷新当前规划。完整字段和状态说明见 [API.md](API.md)。

## 并行修改边界

`server/services/chat-application.ts` 只增加两处必要接线：验证工具结果时校验当前 run/message/revision 对应的持久化草稿；同步接收 `finishRun` 的实际终态，在完成提交冲突时将流终态和助手消息同步标记为失败。没有调整模型参数映射或重构聊天编排。

`server/agents/tools.ts` 的必要接线仅是读取时传入当前 `assistantMessageId`，以及透传工具结果的 `draftId`。`shared/schemas/preview.ts` 增加可选草稿身份和状态，保留旧预览兼容性。`AGENTS.md`、PRD 和 API 中关于“同轮原地改写正式版本”的旧约定已同步修订。

## 版本命名

`VersionItem` 保留所有原字段，并增加 `name`、`nameSource`、`nameRevision`。旧响应缺字段时由共享 schema 默认成 `null`、`null`、`0`；旧数据库升级保留相同默认值。

新正式版本先保存回退名称，提交后才调用现有模型能力。输入包括最终版本内容及相对父版本的变化，要求输出简短具体的中文名称；每次工具调用不单独请求命名。模型请求位于 SQLite 事务外，失败或进程中断不影响已保存行程。AI 写回同时检查用户、规划、数据库版本身份、快照、父版本及命名修订号。用户提交名称后，迟到的 AI 结果作废。

`PATCH /api/plans/:id/versions/:version/name` 使用展示版本号，接收 `{ name, expectedNameRevision }`，返回 `{ version: VersionItem }`。合法名称 trim 后为 1–40 字单行纯文本。改名只更新命名字段，不创建版本，不改规划 JSON、父子关系、当前指针或规划 `revision`。详细错误语义见 [API.md](API.md)。历史快照接口 `GET /api/plans/:id/versions/:version` 继续返回 `{ plan }`。

## 前端联调

本次未修改 `app/utils/api.ts`、工作区前端状态、保存入口、版本树或改名界面。并行任务需要接入：

1. 版本列表消费新增名称字段；旧数据可显示原版本号，名称与行程标题分开。异步命名完成后需刷新版本数据，不能仅依赖规划 `revision` 判断名称缓存是否有效。
2. 改名使用展示版本号和最新 `nameRevision`。409 时保留输入，读取最新名称后由用户确认；不替用户静默覆盖。
3. 工具预览识别草稿状态；预览中的基线版本号不等于草稿已经生成正式版本。流完成后刷新成功快照、正式版本列表及助手消息。
4. 失败、停止或恢复会话时读取服务端草稿并显示“部分成果”与明确恢复操作。已有“保存当前规划”仍保存正式快照，不能把它当作恢复草稿入口。
5. 保留独立手工表单保存和 revision 冲突提示；无变化 `skipped` 不再展示重复保存成功消息。

真实模型命名、浏览器呈现以及版本树/草稿恢复交互需要与前端和实际配置联调；隔离测试不能当成真实供应商验收。
